# TTT Checkpoint Impact — Measured Results — 2026-08-09

First measurement of the model-dependent half of Axiom (absorption, drift
detection, recall) against a real trained checkpoint. Three prior audits
(June, July, 2026-08-08) could not run this comparison because `checkpoints/`
is gitignored and never shipped — every CI box and clean clone runs on
randomly initialized weights. This machine has the checkpoint locally
(`.clinerules`), so this is the first time these claims have been tested
against trained weights rather than the entropy floor.

**All numbers below are measured, not simulated** — commands run directly on
this machine, output pasted with only truncation noted.

## Environment

- Hardware: Intel(R) Core(TM) i5-9300H CPU @ 2.40GHz, 20,320 MB RAM, Windows 11 Home 10.0.26200
- `AXIOM_DEVICE=cpu` (no CUDA toolkit on this machine)
- rustc 1.96.1, release build (`cargo build --release --locked --features tools`)
- Repo commit: `a96d06c89c7c38b6ca3b7b4a789897fe053b8bb6` (main, post-PR#148 merge)
- Checkpoint under test: `checkpoints/axiom_production_bpe.bin` + `checkpoints/axiom_bpe.json`
  - Provenance (`axiom_production_bpe.meta.json`): `vocab_size=8000, d_model=128, n_layers=2, val_ce=5.3876305`, tokenizer path recorded as `/home/runner/work/AXIOM-AETHER/AXIOM-AETHER/checkpoints/axiom_bpe.json` — trained on a GitHub Actions runner (release workflow), dated 2026-07-19. `val_ce=5.39` is well below `ln(8000)=8.99`, consistent with real training having occurred (not simply an artifact of initialization).
- "With checkpoint" config: `AXIOM_PRODUCTION_BPE=1 AXIOM_TOKENIZER=checkpoints/axiom_bpe.json AXIOM_BPE_CKPT=checkpoints/axiom_production_bpe.bin`
- "Untrained" config: `AXIOM_PRODUCTION_BPE=0`, no checkpoint path supplied — engine falls back to `runtime_small()` baseline random weights (legacy 256-vocab hash tokenizer)

## 1. Absorption — does CE move at all?

Command: `axiom run -- sh -c "exit 1"`, reading the `tension:` line from `self_heal.rs`.

| | Untrained (`AXIOM_PRODUCTION_BPE=0`) | With checkpoint |
|---|---|---|
| Output | `tension: CE 5.545 -> 5.545 after 3 absorption pass(es) (10 tokens)  [untrained model: CE is from randomly initialized weights, not a learning signal]` | `tension: CE 7.494 -> 7.402 after 3 absorption pass(es) (35 tokens)` |
| CE delta | 0.000 | **-0.092** |
| Annotation present | yes | no |

- Untrained: `5.545 = ln(256)` exactly — the legacy-tokenizer entropy floor, matching the 2026-08-08 audit's finding precisely.
- With checkpoint: CE moves (`7.494 → 7.402`), the `[untrained model]` annotation correctly does not fire, and the value (`7.494`) sits below `ln(8000)=8.987`. **This is a real, measurable absorption signal that does not exist without the checkpoint.**

## 2. Drift detection — does the 7.03 threshold separate clean from anomalous code?

Command: hand-rolled MCP JSON-RPC driver (`tools/call` → `axiom_evaluate_drift`) against a plain valid Rust snippet ("clean") and a deliberately malformed/garbled snippet ("anomalous"), run once per config against a fresh `axiom --mode mcp` process.

| | Untrained | With checkpoint |
|---|---|---|
| Clean CE | 5.5452 | **8.9872** |
| Anomalous CE | 5.5452 | **8.9872** |
| Margin (anomalous − clean) | 0.0000 | **0.0000** |
| `drift` verdict | `UNAVAILABLE` (`reason=no_master_vibe_baseline`) | `YES` for both (threshold 7.03) |

**No improvement — stated plainly.** Even with the trained checkpoint loaded,
`axiom_evaluate_drift` returns the *exact same* CE (`8.9872 = ln(8000)`, the
entropy floor for this vocab) for both clean and anomalous input — the
7.03 threshold cannot discriminate between them in either configuration; it
just unconditionally reports drift once the checkpoint is loaded (since
8.9872 > 7.03 always) and is entirely disabled without one. This contradicts
the assumption that loading a trained checkpoint fixes drift detection: the
`evaluate_drift` code path appears to hit the same entropy-floor behavior
described in the 2026-08-08 audit even with real weights present — worth
investigating separately, since it suggests `evaluate_drift`'s scoring path
may not be consuming the loaded model the same way the absorption path
(`self_heal.rs`, §1 above) does. Not fixed here — measurement only, per the
task constraints.

## 3. Recall quality

Command: `cargo run --release --features tools --bin eval_recall` (`AXIOM_DEVICE=cpu`).

| | Untrained | With `AXIOM_BPE_CKPT` set |
|---|---|---|
| Loader outcome | `No pre-trained checkpoint found. Initializing with baseline random weights.` | `[eval_recall] could not build production pipeline (error setting ln_f.weight using data from "checkpoints/axiom_production_bpe.bin": shape mismatch in set, lhs: [256], rhs: [128]); using tiny random model` |
| precision@1 (raw) | 0.00 | 0.00 |
| precision@3 (raw) | 0.00 | 0.00 |
| precision@1 (mean-centered) | 0.20 | 0.20 |
| precision@3 (mean-centered) | 0.60 | 0.60 |

**No improvement — and no valid comparison was actually possible.**
`eval_recall`'s embedder pipeline expects a `[256]`-shaped `ln_f.weight`
(the legacy hash-tokenizer architecture) and the production BPE checkpoint
is `[128]`-shaped — the load fails and the tool silently falls back to "tiny
random model" in *both* configurations. The identical precision numbers
above are not evidence the checkpoint doesn't help recall; they are evidence
`eval_recall` never actually loaded it. This is a distinct, previously
unknown gap from the CE-floor problem: the recall eval tool itself needs a
compatible embedder checkpoint (`AXIOM_EMB_CKPT`, default
`checkpoints/axiom_embedder.bin`, absent on this machine) or an update to
accept the BPE model shape before recall@k can be measured at all.

## 4. Compression — control

Command: `axiom bench axiom_engine_rs/src` (structural skeleton compression; expected to be model-independent).

| | Untrained | With checkpoint |
|---|---|---|
| Files measured | 121 | 121 |
| Signatures kept (round-trip) | 2229 (2229/2229 = 100.0%) | 2229 (2229/2229 = 100.0%) |
| Original tokens | 177,270 | 583,521 |
| Skeleton tokens | 30,975 | 77,843 |
| Token savings | 82.5% | 86.7% |

**This is not "no difference" — flagging as required.** File count and
signature round-trip fidelity (the actual structural-extraction logic) are
identical across configs, confirming skeleton extraction itself is
model-independent as claimed. But the raw and skeleton token *counts* differ
by more than 3x between configs, because `AXIOM_PRODUCTION_BPE` switches the
active **tokenizer** (BPE, vocab 8000) alongside the model, and tokenizer choice
changes how the same 121 files are chunked into tokens — a confound the task
description didn't anticipate. The headline "82.4% compression" figure from
prior audits is tokenizer-dependent, not a fixed property of the
architecture; it should be quoted with which tokenizer was active.

## Summary

| Claim | Verified with real checkpoint? |
|---|---|
| Absorption moves CE | **Yes** — real signal, `7.494 → 7.402`, absent without checkpoint |
| Drift detection discriminates anomalies | **No** — identical CE for clean/anomalous even with checkpoint loaded |
| Recall quality improves | **Not measurable** — `eval_recall` never loads this checkpoint shape |
| Compression is model-independent | **Partially** — structural extraction yes, token-count metric no (tokenizer-confounded) |

Two of four claims audited previously as "unverified due to no checkpoint" are
now "verified false or not measurable even with a checkpoint," not simply
"blocked." Absorption is the one component functioning as designed. Drift
detection and recall evaluation each have a distinct, previously-undiscovered
bug (entropy-floor-equivalent CE in `evaluate_drift`; shape-incompatible
checkpoint in `eval_recall`) that a checkpoint alone does not fix.
